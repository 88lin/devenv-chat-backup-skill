# 方案架构与设计决策

## 问题背景

华为云 DevEnv 是基于容器的开发环境，使用 overlay 文件系统：

```
overlay 文件系统结构:
┌─────────────────────┐
│   Upper (overlay)    │  ← 可写层，所有修改写在这里
├─────────────────────┤
│   Lower (image)      │  ← 只读层，容器镜像
└─────────────────────┘
```

**容器重建时，Upper 层被完全清除**，只保留 Lower 层（镜像原始内容）。这意味着：
- 用户安装的软件 → 丢失
- 修改的配置文件（.bashrc 等）→ 丢失
- 创建的数据文件 → 丢失
- 聊天会话、记忆数据库 → **全部丢失**

## 方案选型

### 候选方案对比

| 方案 | 可靠性 | 成本 | 复杂度 | 容器重建后可恢复 | 结论 |
|------|--------|------|--------|-----------------|------|
| GitHub 私有仓库 | ⭐⭐⭐ | 免费 | 低 | ✅ git clone | **采用** |
| 华为云 OBS | ⭐⭐⭐ | 收费 | 中 | ✅ obsutil | 否决 |
| 本地备份 | ⭐ | 免费 | 低 | ❌ 一起丢 | 否决 |
| 不备份 | - | 免费 | - | ❌ | 否决 |

### 为什么选 GitHub 私有仓库？

1. **免费**：私有仓库免费，不产生任何费用
2. **可靠**：GitHub 基础设施稳定，数据不会丢
3. **git 版本控制**：天然支持增量、版本追溯、回滚
4. **恢复简单**：一条 `git clone` 即可恢复全部数据
5. **DevEnv 网络兼容**：`git clone` 不受 DNS 限制（curl 受限）

## 架构设计

```
┌──────────────────────────────────────────────────────┐
│                   DevEnv 容器                         │
│                                                       │
│  ┌─────────────────┐                                 │
│  │  聊天数据目录     │  /root/.huawei/hwcloud/         │
│  │  ├── sessions/   │  ← 聊天会话 (*.jsonl)           │
│  │  ├── memory.db   │  ← 语义记忆                     │
│  │  ├── audit.db    │  ← 审计日志                     │
│  │  ├── settings.json│  ← 用户设置                    │
│  │  ├── SOUL.md     │  ← Agent 人格                   │
│  │  └── user_info.json│  ← 用户信息                   │
│  └────────┬────────┘                                 │
│           │ cp -rf                                   │
│           ▼                                          │
│  ┌─────────────────┐                                 │
│  │  仓库本地副本     │  /root/chat-backup-new/        │
│  │  ├── hwcloud-data/│  ← 备份的数据                  │
│  │  ├── chat-backup.sh│  ← 备份脚本                   │
│  │  └── README.md   │  ← 恢复命令                    │
│  └────────┬────────┘                                 │
│           │ git commit + push (每120秒)               │
│           ▼                                          │
│  ┌─────────────────┐                                 │
│  │  守护进程         │  setsid + nohup + while        │
│  │  PID: /var/run/  │  日志: /var/log/chat-backup.log│
│  └─────────────────┘                                 │
│                                                       │
│  ┌─────────────────┐                                 │
│  │  .bashrc         │  新终端 → daemon (仅备份，不 restore)      │
│  └─────────────────┘                                 │
└──────────────────────────────────────────────────────┘
                    │
                    │ git push/pull
                    ▼
         ┌────────────────────┐
         │  GitHub 私有仓库     │
         │  YOUR_USER/         │
         │  YOUR_REPO (private)│
         └────────────────────┘
```

## 数据流

### 备份流程（每120秒）

```
本地数据 → cp -rf → 仓库本地副本 → git add → git commit → git push → GitHub
```

### 恢复流程（手动执行，容器重建后一次性）

```
GitHub → git pull → 仓库本地副本 → cp -rf → 本地数据
```

> ⚠️ restore 不在 .bashrc 中自动执行（避免覆盖运行中数据库导致损坏）。
> 容器重建后请手动执行一次：`/root/chat-backup.sh restore`

### 容器重建恢复流程（手动一次性）

```
1. 配置 git 凭证
2. git clone 仓库
3. cp 脚本到 /root/
4. 执行 setup（恢复数据 + 启动守护进程 + 配置 .bashrc）
```

## 设计决策

### 1. 为什么用 `cp -rf` 而不是 `rsync`？

DevEnv 精简环境没有 rsync。`cp -rf` 虽然不如 rsync 高效（不能增量同步），但功能足够：
- 复制新文件 ✅
- 覆盖已修改文件 ✅
- 删除已删除文件 → 需要手动遍历清理（脚本中已实现）

### 2. 为什么用 `setsid + nohup + while` 而不是 `crontab`？

DevEnv 没有 cron 服务。`setsid + nohup + while` 组合：
- `setsid`：创建新会话，脱离终端
- `nohup`：忽略 SIGHUP，终端关闭不死
- `while + sleep`：循环执行，替代 cron 定时

### 3. 为什么所有 git 命令加 `timeout 30s`？

DevEnv 网络不稳定，git 命令可能因网络问题无限等待。timeout 确保：
- 网络抖动时不会卡死守护进程
- 不会堆积僵尸进程（D 状态）
- 30 秒足够完成正常操作

### 4. 为什么恢复命令保存在 GitHub README？

恢复命令本身也在 overlay 层，容器重建后一起丢失。保存在 GitHub 仓库的 README 中：
- 容器重建后打开 GitHub 网页即可看到
- 不依赖本地任何文件
- 复制粘贴即可执行

### 5. 为什么备份间隔是 120 秒？

- 太短（如 10 秒）：git 操作频繁，可能堆积
- 太长（如 600 秒）：丢失最近几分钟的对话
- 120 秒：平衡点，最多丢失 2 分钟数据
